ReLiC Share is the public engineering record for the ReLiC continuity system. The verified milestone demonstrates that a GitHub change can become a bounded OBSERVATION, cross a private AWS ingestion boundary, persist in durable storage, and later be retrieved by ChatGPT through a physically read-only MCP path without silently promoting the observation to canon.

Problem

AI continuity usually loses the reason a state exists.

A current answer can be correct while its history is missing. A new build can work while hiding the failed builds that taught the system what not to do. ReLiC addresses that gap by separating identity, representation, truth, provenance, status, and authority instead of collapsing them into one mutable summary.

Identity ≠ representation · Representation ≠ truth · UNKNOWN ≠ FACT · MEMORY ≠ CANON · Observation ≠ Canon

Verified architecture

End-to-end continuity is complete.

1 · GitHubRepository change on the observed branch.
2 · ActionsObservatory CI validates and packages evidence.
3 · OIDCGitHub assumes a branch-scoped AWS role; no stored GitHub write token.
4 · LambdaPrivate ingestion bridge validates the evidence and holds write authority.
5 · ReLiC HostPrivate host writes the bounded event to durable EFS-backed storage.
6 · MCPReLiC MCP opens the database read-only and exposes bounded retrieval.
7 · ChatGPTSecure MCP Tunnel returns the preserved event and provenance.

This architecture proves the tested path. It does not claim universal AI safety, universal correctness, or automatic canon promotion.

Evidence classes

What each label means

OBSERVATIONSomething ReLiC recorded with provenance. It is not automatically truth or canon.
EVIDENCEMaterial that supports verification: logs, hashes, test results, source state, runtime state, and preserved artifacts.
REPRESENTATIONA page, summary, model output, diagram, or other view of evidence. Representation is not the evidence itself.
CANONGoverning project truth promoted through the applicable authority process. Observation cannot promote itself.

Security model

Write authority stays private.

  • GitHub uses OIDC rather than a stored ReLiC write token.
  • The AWS role is scoped to the observed branch and the bounded ingestion function.
  • The ingestion Lambda validates the envelope before requesting private write credentials.
  • The ReLiC host receives private ingestion; GitHub does not write directly to the database.
  • The MCP container mounts the durable data path physically read-only and opens SQLite with mode=ro plus query-only semantics.
  • The Secure MCP Tunnel is outbound from the ReLiC runtime; the MCP database reader has no ReLiC write authority.

Failure history

The report keeps the failures that made the proof stronger.

  1. Runs #22 and #23 — import regression. CI failed during test collection with ModuleNotFoundError: No module named 'validation'. OIDC was not exercised in those failed runs. The import path was corrected instead of treating a later green run as if the failures never happened.
  2. Run #24 — real OIDC ingestion succeeded. The workflow completed, GitHub assumed the OIDC role, Lambda returned a successful bounded ingestion response, and the resulting CODE_CHANGE event was stored as OBSERVATION.
  3. Live MCP read failure — SQLite reported “database disk image is malformed”. Forensics preserved the DB, WAL, and SHM before repair. A coherent copy passed both quick_check and integrity_check, so the evidence did not support claiming logical database destruction.
  4. Architecture defect identified — WAL on shared EFS with multiple possible writers/readers. The writer was changed to rollback-journal DELETE mode; MCP was changed to a physically read-only mount and read-only SQLite connection.
  5. First hardened rev8 launch failed before containers started. The task could not reach the private Secrets Manager interface endpoint because that endpoint's security group did not permit HTTPS from the ReLiC ECS host security group.
  6. Scoped network correction. TCP 443 from the ReLiC host security group was added to the Secrets Manager endpoint security group; no public CIDR was introduced.
  7. Second rev8 launch succeeded. The task reached RUNNING/HEALTHY, MCP became HEALTHY, and the recovered database remained intact.

Recovery and verification

Recovery was evidence-preserving, not destructive.

  • The live SQLite files were copied to a timestamped forensic recovery directory before mutation.
  • The coherent preserved copy passed quick_check = ok and integrity_check = ok.
  • All old standalone writer-capable tasks were stopped before journal conversion.
  • The consolidated database was converted from WAL to rollback journal DELETE mode.
  • Post-recovery database SHA-256: 4011371f636ef418de0355d41e5de0d33886bfaa85a00673e699724e2c29c21c.
  • Post-recovery event count remained 5 before any intentional new write.
  • The critical GitHub event retained status OBSERVATION and the exact expected payload hash.
  • The hardened runtime was then queried from ChatGPT through the live ReLiC connector, independently closing the readback path.

Read-only interface

What ChatGPT can retrieve

  • relic_context_pack — bounded continuity relevant to a query.
  • relic_search — bounded search across stored event fields and payload text.
  • relic_get_event — one immutable event by ID.

These tools retrieve representation of stored evidence. They do not grant authority to mutate ReLiC or promote an observation into canon.
